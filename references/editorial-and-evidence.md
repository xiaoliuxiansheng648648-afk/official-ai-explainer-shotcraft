# 编辑与事实底稿

## 目标

先弄清产品真正做什么，再决定怎么讲。成片要让没有专业背景的人在几十秒内回答三个问题：它是什么、与我有什么关系、它做不到什么。第一个问题的答案要在开头 2 秒内说出来。

## 官方证据优先级

按下列顺序寻找同一事实的依据：

1. 产品官方文档、API 参考和限制说明。
2. 官方发布博客、新闻稿和产品页面。
3. 官方演示视频、官方账号发布的截图或案例。
4. 创始人或公司成员的公开说明。
5. 第三方报道只用于补充背景，不单独支撑核心产品结论。

“搜索结果摘要”和转述文章不是最终证据。打开原页面核对上下文、日期和适用版本。

## 事实台账

写稿前至少记录：

| 字段 | 内容 |
|---|---|
| claim | 准备告诉观众的具体事实 |
| source_url | 原始官方网址 |
| source_type | docs / blog / demo / product page |
| captured_at | 核对或采集时间 |
| exact_support | 页面中的原句、画面或时间码 |
| confidence | confirmed / qualified / unclear |
| intended_scene | 准备用在哪一段 |
| source_kind | official / own-product / illustration / media，决定画面角标 |

`qualified` 的事实必须把限定条件讲出来；`unclear` 不进入确定性口播。

## 大白话写作规则

- 第一遍只写“谁遇到了什么麻烦，它替谁做了什么，结果有什么变化”。
- 每出现一个术语，立刻给出可观察的行为或日常类比。
- 优先使用具体动词：筛选、判断、填写、比较、执行、检查。少用“赋能、重塑、颠覆、生态”等空词。
- 一句话只承担一个主要判断。口播中较长的中文句子应拆开，让字幕能自然换行；单句尽量不超过 24 个字，手机小窗里的字幕才读得完。
- 参数只有在它会改变普通人的体验时才出现；出现时同时解释“这意味着什么”。
- 不把“可以被开发者集成”说成“普通人现在已经可以直接使用”。
- 不把演示结果说成稳定、普遍或无条件的能力。

## 六段写稿提示

### 1. 一句话定义

使用“它不是先做 X，而是帮 Y 完成 Z”或“它负责在 A 的时候做 B”这类句式。定义必须能脱离品牌词单独成立。第一句口播就是本期结论，不先铺陈背景；镜头标题与这句话一致。

### 2. 具体差异

选择同一个任务比较旧方式和新方式。避免只说“更快、更强、更智能”；说明少了哪个步骤、多交付了什么结果。

### 3. 日常场景

每个场景都写成“输入/处境 → 判断或动作 → 用户得到的结果”。优先真实、常见且有官方依据的场景。

### 4. 核心能力

可以保留术语，但画面和口播必须同时给出口语翻译。技术解释的深度以帮助理解为限，不以展示专业为目的。

### 5. 边界

说明任务需要满足的前提、容易失败的条件和不适用场景。边界不是负面补丁，而是建立可信度的核心镜头。

### 6. 落点

告诉观众更可能在哪里遇到它，而不是默认所有人都会打开一个独立产品。CTA 应延续主题，避免生硬要求点赞关注。

作者有账号口吻时，这一段收束到作者判断：先说“我的判断是……”，再给一句理由。判断不能写成事实；引用自己的经历时只用作者提供过的真实经历。

## 配音前文本检查

- 品牌、产品、人物和缩写的读法已确认。
- 多音字在当前语境下的读音已确认。
- 数字、版本号、网址和英文缩写适合口播。
- 强调词确实出现在最终口播文本中。
- 没有为了发音方便改变事实含义。
- 需要发音字典时记录 `{key, value, caseSensitive}`；例如语境中的“藏”应读 `cang2`。
